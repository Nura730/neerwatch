# NEERWATCH — Project Context

## Product Purpose

NEERWATCH is a water-quality monitoring prototype for field health workers. Field staff collect household water samples, run rapid tests (TDS, pH, turbidity, coliform), and record observations on mobile devices. The system aggregates test results, detects spatial-temporal clusters of poor water quality, generates alerts, and presents ward-level summaries on a dashboard.

**IMPORTANT — Synthetic Data Notice:**
All observations in the NEERWATCH prototype are synthetic demo data generated for development and demonstration purposes. They do not represent real public-health measurements and must not be presented, shared, or interpreted as such.

---

## Offline-First Workflow

Field workers operate in areas with unreliable connectivity. The mobile frontend:

1. Records observations locally (with a client-generated `clientId`).
2. Queues observations for synchronization when connectivity is restored.
3. Calls `POST /api/tests/sync` to upload batches of observations.
4. The backend deduplicates using `clientId` so repeated sync calls are safe.

## Backend Responsibilities

- Persist water-test observations to MongoDB.
- Deduplicate observations using `clientId`.
- Convert frontend `{ lat, lng }` coordinates to MongoDB GeoJSON `{ type: "Point", coordinates: [lng, lat] }`.
- Run spatial-temporal cluster detection on persisted observations.
- Generate alerts from detected clusters.
- Aggregate observations by ward.
- Serve REST API responses in the agreed envelope format.
- Accept rainfall context data and expose it via API.

## Frontend Responsibilities (for reference only — do not modify)

- Collect test observations on mobile devices.
- Assign a unique `clientId` per observation before syncing.
- Pass coordinates as `location: { lat, lng }`.
- Render dashboard, map, cluster, alert, and ward views by consuming the backend REST API.

## Water-Test Data Model

Each observation stored in MongoDB contains:

| Field | Type | Notes |
|-------|------|-------|
| `clientId` | String | Unique ID generated by client; idempotency key |
| `householdId` | String | Identifies the sampled household |
| `testType` | String | `"TDS"` \| `"pH"` \| `"turbidity"` \| `"coliform"` |
| `result` | Number | Numeric test result value |
| `testedAt` | Date | ISO 8601 timestamp of when the test was performed |
| `location` | GeoJSON Point \| null | Stored as `{ type: "Point", coordinates: [lng, lat] }` |
| `wardId` | String | Ward identifier |
| `createdAt` | Date | Server-assigned insertion timestamp |

## GeoJSON Coordinate Convention

MongoDB GeoJSON stores coordinates as **[longitude, latitude]** (x, y order).

The frontend submits coordinates as:
```json
{
  "location": {
    "lat": 18.5204,
    "lng": 73.8567
  }
}
```

The backend converts to GeoJSON before persistence:
```json
{
  "location": {
    "type": "Point",
    "coordinates": [73.8567, 18.5204]
  }
}
```

**This conversion happens in the backend. The frontend always uses `lat`/`lng`.**

API responses return coordinates in the frontend-friendly `{ lat, lng }` format, not raw GeoJSON arrays.

---

## clientId / Idempotency Requirements

- Each observation must carry a `clientId` assigned by the mobile client before syncing.
- `clientId` is the idempotency key. The backend uses it to detect duplicate observations.
- If a `POST /api/tests/sync` batch contains a `clientId` already present in the database, that observation is counted as a duplicate and skipped — no error is raised and no duplicate document is created.
- Repeated synchronization of the same batch must always be safe (idempotent).

---

## Missing-Location Behavior

- `location` is optional. Observations recorded in areas without GPS signal may omit it.
- Observations without `location` are stored with `location: null`.
- Observations with `location: null` are persisted and included in list/dashboard responses.
- Observations with `location: null` **cannot participate in spatial cluster detection** and are excluded from map responses.

---

## Synchronization Requirements

- The sync endpoint accepts an array of observations in a single request.
- The backend processes each observation independently.
- The response reports: `processed`, `created`, `duplicates`, `failed` counts.
- Partial success is acceptable; failed items are reported but do not block successful items.

---

## Transparent Spatial-Temporal Cluster Detection

Cluster detection is rule-based and deterministic — no ML. The algorithm:

1. Groups observations by `testType`.
2. For each group, applies a sliding spatial-temporal window.
3. If the count of failing observations within the window meets the threshold, a cluster is recorded.

### Prototype Cluster Parameters

| Parameter | Value |
|-----------|-------|
| Spatial radius | 500 metres |
| Temporal window | 7 days |
| Minimum failing observations | 3 |

These parameters are prototype values and may be adjusted. They must not be hardcoded in business logic; expose them as configuration constants.

---

## Rainfall Context

- Rainfall readings are stored separately and linked to ward/date.
- The `GET /api/rainfall` endpoint exposes rainfall data for frontend overlay.
- Rainfall data is synthetic in the prototype.

---

## Alert Behavior

- An alert is generated when a new cluster is detected.
- Each alert references its source cluster.
- Alerts carry a `severity` field. Specific severity thresholds are determined during implementation — do not invent or hardcode medical/public-health threshold values.
- Duplicate alerts for the same cluster are suppressed.

---

## Ward Aggregation

- `GET /api/wards` returns per-ward summary statistics aggregated from observations.
- Summary includes: total tests, pass count, fail count, failure rate, most recent test date.

---

## API Response Conventions

All endpoints return JSON in the following envelope:

**Success:**
```json
{
  "success": true,
  "data": {}
}
```

**Error:**
```json
{
  "success": false,
  "message": "Human-readable error description"
}
```

HTTP status codes follow standard semantics (200, 201, 400, 404, 500).

### id vs _id Convention

MongoDB documents carry an internal `_id` field. The public API **never exposes `_id`**. All API responses map `_id` to a string field named `id` before returning data to the frontend. This applies to cluster and alert documents.

## Security Constraints

- No authentication is required in the prototype phase.
- Do not add JWT, API keys, or session middleware at this stage.

---

## Validation Requirements

- `clientId`, `householdId`, `testType`, `result`, `testedAt`, and `wardId` are required on each observation.
- `testType` must be one of: `"TDS"`, `"pH"`, `"turbidity"`, `"coliform"`.
- `result` must be a finite number.
- `testedAt` must be a valid ISO 8601 date string.
- If `location` is provided, both `lat` and `lng` must be present and be valid finite numbers.
- `lat` must be in range [-90, 90]; `lng` must be in range [-180, 180].

---

## Error Handling

- Validation errors → `400 Bad Request` with `{ success: false, message: "..." }`.
- Not found → `404 Not Found`.
- Unexpected server errors → `500 Internal Server Error`; do not leak stack traces in responses.
- Log errors to the console in development; use structured logging in production.

---

- Tests must not share state between runs; use `beforeEach`/`afterEach` to clean collections.
- Cluster detection logic must have dedicated unit tests covering the prototype parameters.
